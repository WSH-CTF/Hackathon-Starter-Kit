# 📜 Hackathon Rules & Guardrails

## Theme
Cybersecurity — build tools, apps, or demos related to security, privacy, or safety online.
Projects should be **defensive and educational**, not offensive.

## ✅ Allowed
- Building your own vulnerable "practice" app and then a tool to scan/test **that same app**
- Using OWASP Juice Shop or another intentionally-vulnerable app provided by organizers as a scan *target*
- Password strength / breach-checking tools using public APIs (e.g., Pwned Passwords)
- Phishing/malware URL detectors using public threat-intel APIs (Google Safe Browsing, VirusTotal)
- Encryption, authentication, and privacy tools
- Security awareness games, quizzes, and training platforms
- Data visualization of **provided or synthetic** security datasets (e.g., sample pcap files, sample logs)
- Static code analysis / secret-scanning tools run on your **own** codebase
- Firewall rule engines, intrusion detection/prevention demos, and network traffic
  visualizers — as long as they run against the **provided sample traffic data**,
  **synthetic/generated data**, or a **private virtual network you set up yourselves**
  (e.g., a local Docker/VM lab), never the venue Wi-Fi or any real school network

## ❌ Not allowed
- Scanning, probing, or attacking **any external system** you don't own or have explicit written permission to test — this includes the school's network, other teams' projects, competition infrastructure, or any third-party website
- Sniffing or intercepting network traffic on the shared venue Wi-Fi
- Building or demonstrating malware, ransomware, keyloggers, or any tool designed to gain unauthorized access
- Social engineering real people (staff, other participants, judges) as part of a demo without their prior consent
- Scraping or attempting to access real user data without consent
- Any activity that violates your country's computer misuse laws (e.g., unauthorized access laws) or your school's IT acceptable use policy

## Judging will consider
1. **Technical execution** — does it work, is the code reasonably clean?
2. **Relevance to theme** — clear security/privacy angle
3. **Creativity** — original take on a problem
4. **Presentation** — clear live demo, explained well in the time allowed
5. **Responsible design** — did the team think about ethics/safety of what they built?

## If you're unsure whether something is in scope
Ask an organizer/mentor before you build it. When in doubt, keep everything **self-contained**:
your own app, your own data, your own devices.

## Consequences
Any team found violating the "not allowed" section (especially attacking real
infrastructure) will be disqualified immediately, and organizers reserve the right to
report serious violations (e.g., unauthorized access attempts) to school administration.
